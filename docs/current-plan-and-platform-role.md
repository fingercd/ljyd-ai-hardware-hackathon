# 当前总结、执行策略与灵机一动平台职责

日期：2026-10-31。依据已保存赛题/开发文档、固定SDK源码25cb6e51、本机启动日志和最近一次平台只读核查。没有继续泛搜模型目录，也没有新增刷写、配网或平台配置操作。

## 一句话结论

项目已经证明“板子能启动、联网，并对固定测试图运行本地姿态模型”；还没有证明“奶龙能用真实摄像头监督学习并通过平台/硬件完整反馈”。灵机一动的主要作用是**产品与设备接入、语音Agent配置和会话、技能/场景与设备功能连接**，不是未经核实的通用YOLO托管服务器。

## 平台到底解决什么

### 1. 把设备接入变成产品，而非一块孤立MCU

开发文档区分产品、设备、产品身份与物模型。SDK的 `ljyd_cloud_init()` 用产品ID/密钥配置IoT连接，并注册属性和方法回调。产品功能定义说明设备有哪些属性、服务与事件，固件需实现相同语义。

这能复用已有接入/鉴权/消息基础；但我们仍须把自己的产品、当前设备和奶龙Agent正确关联。当前“cloud connected”只说明基线IoT连接成功，不能证明属于此草案或当前网页账号下的产品。

### 2. 配置一个能持续对话的奶龙

实际设置页可见角色、路由/模型、对话策略、记忆、语音识别、音色和语速。SDK有qm_agent会话框架、Opus音频、Agora传输及ASR/TTS/文本/状态事件，提供对接现成服务的基础。

平台承担拟定的角色对话、任务协商、解释与工具选择；无需为原型先自建一整套聊天服务。这里描述配置与代码支持，不表示本项目已完成两轮实板语音或平台服务性能验证。

### 3. 把语言意图连接到可实现的设备功能

固定25cb的IOT属性表**实际只有音量控制**；另有chat退出、资源播放、闹钟等独立方法/组件。云端属性下发，经固件查表才写硬件并上报状态。

因此“声音大一点”是可优先验证的真实产品操作：Agent/平台理解→下发匹配属性→固件音量回调→语音板变化。反之，添加“设备控制”插件或提示词写“喷水”，不会自动产生泵驱动和安全停止功能。

### 4. 组织场景和技能，不等于自动拥有任意工作流

实际可见插件包括设备控制、闹钟、番茄时钟、资源播放等。智能场景表单是语料匹配触发、从所选产品功能列表选执行项；高级工作流具体节点/外部接口尚未深入核实。

可以将它用于学习开始、计时、休息、解释和恢复等交互，但视觉事件能否主动触发Agent、暂停能否改变电脑状态、场景能否调用自定义泵服务，都须针对真实接口验证，不能仅凭菜单存在就写成已完成。

### 5. 留存应用配置与调用证据

开发文档描述设备状态、配置版本、固件/功能定义关联和调试预览等。代码与平台配置是两份资产：后续要同时记录源码/SDK/固件版本、Agent发布版本、插件/场景配置和真实调用结果；密钥不入Git。固件/OTA管理属于后续可评估能力，当前不以其可用作前提。

## 平台不能替我们自动完成的部分

- 没有证实平台提供COCO80类YOLO推理服务、自定义.pt权重托管或实时SPI视频输入。
- 多模态“认知模型”、拍照搜题和图生图目录不能代替姿态/手机/疲劳检测证据。
- 不会自动接通摄像头驱动、UYVY转换、帧传输、电脑推理和坐标映射。
- 不会替代持续窗口、提醒计数、恢复条件、离席/未知处理或板端泵限时和硬停用。
- LLM说“已暂停/已喷水”不代表业务状态或GPIO已经改变；必须有执行路径与结果核对。

## 推荐架构与分工（待实现部分明确保留）

1. 指定SPI摄像头负责真实采集，ESP32-S3保留语音、联网和设备执行。
2. 优先复用现有本地pose做采集/关键点验证；若需要80类手机检测和更多脸部信息，电脑是重视觉候选。当前电脑RTX4060 Laptop约8GB显存，只证明有试跑条件，没有模型速度实测。
3. 电脑承担合适的视觉处理、弹窗及确定性会话规则。SPI→电脑的Wi-Fi传图尚未开发；不能用电脑自带摄像头冒充指定SPI验收。
4. 平台承担奶龙对话、任务/休息协商及至少一项与学习相关的真实能力调用。
5. 视觉状态如何进入Agent、平台的暂停/恢复如何改变真实会话状态，是关键集成接口。SDK通用上报函数并不证明云端有任意事件触发能力；必须取得字段/示例并验证。
6. 板端最终限制泵脉冲和失联安全关断，物理开关独立于电脑、网络和LLM。

这是一条推荐方案，不是已完成的数据链。部署在电脑上的127.0.0.1服务不会天然被云端平台访问；需要已支持接口或受控桥接，不公开裸露的本地控制服务。

## 任务优先级与验收

| 优先级 | 任务 | 完成证据 |
|---|---|---|
| P0-A | 补齐奶龙必填项并实际预览；确认产品、设备和Agent的关联路径 | 两轮真实对话，草案/发布状态和配置记录 |
| P0-A | 利用现固件已支持的音量或学习闹钟完成一次平台调用 | 平台调用记录＋对应设备日志＋实际音量/响铃反馈，不靠文字宣称 |
| P0-B | 确认指定SPI相机/转接板接线、供电及GPIO4/8占用，保存一张真实图 | 可见且方向/色彩正确的真实帧；字节计数不够 |
| P0-B | 固定同一人并接通实时姿态输入，测实际延迟、丢帧和内存/语音并发 | 帧ID/采集与结果时间、关键点随真实动作变化 |
| P0-C | 取得视觉事件→Agent和平台指令→实际会话状态的受支持接口 | 一条可重复的事件/命令/结果闭环，参数和失败路径可说明 |
| P1 | PC端COCO80手机候选检测与坐姿/任务信息组合，疑似瞌睡单独评估 | 手机放桌、查资料、写字低头、离席、遮挡等反例；不只正例 |
| P1 | 两次提醒＋观察期仍未改善后第三阶段，完成弹窗、恢复与去重 | 无泵模拟/干运行可重复；未知/离线/暂停不升级 |
| P2 | 独立泵、电源与驱动、实际水路、硬停用 | 限时/断线/取消/重启均可靠关断，实测水量和供电，再接状态机 |
| 收尾 | 外壳实装、两工作流、三类情境、两种硬件反馈、演示与交付 | 赛题清单逐项实证；最终验收后再打hackathon-final |

软件可先按主办方“交互创建→预览→标准接入→个性化”推进，板子已联网不意味着可以跳过前两步。外壳沿用已认可概念做实装核对，不让反复外观迭代挤占核心链路验证。

## 两条工作流的建议

- **开始专注与规则协商**：用户说明任务→奶龙澄清是否允许手机查资料、时长及提醒模式→实际保存/同步规则→关联学习计时/设备反馈。
- **监督提醒与恢复**：持续可见证据→询问/提醒→观察是否改善→必要时升级；用户可解释、休息、暂停并恢复→真实控制状态和设备反馈同步。

这比把“响一次、弹一次、喷一次”算三条工作流更合理。至少三类使用情境可体现开始/监督/休息或提醒/恢复等；不把它擅自扩写成必须三种坐姿，同时指定SPI坐姿要求仍保留。

## 现在最值得向平台技术人员确认的问题

1. 已联网的这块设备如何关联自己的产品和奶龙Agent？能否保留现固件/配网完成绑定，还是必须更换产品身份？
2. 设备/电脑产生的坐姿或手机候选事件，如何通过官方接口触发Agent？请提供一条真实输入、输出与示例代码，而非仅模型名称。
3. 自定义暂停/恢复/受限动作服务如何定义、调用和回执？智能场景是否支持设备事件而不只是语料？
4. 若提供云视觉或模型托管，准确入口、输入格式、返回字段、限制和费用是什么？没有该服务时，指定SPI采集＋电脑推理的分工是否符合现场要求？
